# V0.6.1 Plugin Skills Read-Only Source Design

## Goal

V0.6.1 先完成 Plugin Skills 来源调研与只读接入设计，为后续把 Codex 插件提供的 Skills 纳入 `Available` 做准备。

本版目标不是马上扩大扫描范围，而是确认：哪些插件目录和清单可以作为可信候选、UI 应如何解释 Plugin 来源、以及哪些能力必须继续交给 Codex 官方插件系统处理。

## Product Scope

V0.6.1 包含：

- 记录 Codex 插件 Skill 的产品定义：由已安装或已缓存的 Codex 插件提供的只读 Skills。
- 验证本机可见的插件元数据结构，例如插件版本目录下的 `.codex-plugin/plugin.json` 和 `skills` 相对路径。
- 设计 `Available` 未来扩展为 `All Sources / Personal / Plugin / System` 的信息架构。
- 明确 Plugin 来源只读，不进入 Library 或 Installed 的所有权语义。
- 明确 Plugin 发现必须优先基于插件清单和元数据，不允许把 `.codex/plugins/cache` 全量扫描作为正式产品能力。
- 更新项目状态、路线图和决策记录，方便后续电脑继续实施。

V0.6.1 不包含：

- 真实接入 Plugin Skills 扫描。
- 增加 `Plugin` 筛选入口到当前 App。
- 插件安装、卸载、启用、禁用或更新。
- 读取插件 hooks、runtime、MCP、apps 或权限配置并作为 SkillDock 可管理能力。
- 修改 Library、Installed、GitHub 导入、AI 翻译、设置窗口或打包流程。

## Findings

当前本机 Codex 插件缓存中存在两类可观察结构：

- 远程插件根目录下的 `.codex-remote-plugin-install.json`，包含 `schema_version` 和 `remote_plugin_id`。
- 具体版本目录下的 `.codex-plugin/plugin.json`，包含插件 `name`、`version`、`description`、`interface.displayName`、`skills` 相对路径等信息。

示例结构：

```text
~/.codex/plugins/cache/openai-curated-remote/superpowers/
  .codex-remote-plugin-install.json
  6.2.0/
    .codex-plugin/plugin.json
    skills/*/SKILL.md
```

这个结构可以作为可行性验证依据，但仍位于 Codex cache 下。除非后续确认它是稳定公开契约，否则 SkillDock 不应在正式功能中直接承诺依赖它。

## Recommended Approach

推荐采用“清单优先、只读发现、保守展示”的方案。

对比：

- 方案 A：只读设计与可行性验证。产品体验稳，避免误导用户；实现成本低；后续维护风险最低。推荐。
- 方案 B：直接扫描插件版本目录并展示 Plugin。用户马上能看到更多 Skills，但容易把缓存、旧版本或未启用插件误认为当前可用；维护风险高。
- 方案 C：只做 UI 占位。实现最轻，但不能验证真实数据，也无法减少后续实施不确定性。

V0.6.1 选择方案 A。

## Future Source Model

后续实现时，`AvailableSkillSource` 可以扩展为：

```text
personal
plugin
system
```

语义保持清晰：

- `Personal`：用户个人 Skills，当前为 `~/.agents/skills`。
- `Plugin`：Codex 插件清单声明的 Skills。
- `System`：Codex 系统内置 Skills。

Plugin 不应编码成 Agent Target，也不应计入 Installed。它只代表“Codex 可能通过插件提供的能力来源”。

## Discovery Rules

后续实现应遵循：

- 从已识别插件根目录进入。
- 先读取插件清单，例如 `.codex-plugin/plugin.json`。
- 只有清单显式声明 `skills` 相对路径时，才扫描该目录下的 `SKILL.md`。
- 每个 Plugin Skill 的物理副本记录来源为 `available(.plugin)`，并保留插件名、版本和路径作为后续展示所需元数据。
- 插件清单解析失败时跳过该插件并记录扫描问题，不阻断 Personal 和 System。
- 多版本插件同时存在时，不默认全部展示；必须先确认当前启用或最新可用版本的判定规则。

禁止规则：

- 不递归扫描整个 `.codex/plugins/cache` 寻找所有 `SKILL.md`。
- 不把 `.codex/plugins/cache` 下的任意目录都视为已安装插件。
- 不读取或执行 hooks。
- 不修改插件目录内容。

## Interface Direction

未来接入后，`Available` 顶部来源筛选扩展为：

- `All Sources`
- `Personal`
- `Plugin`
- `System`

列表中来源标签增加 `Plugin`。如果同一 Skill 同名同 Hash 同时来自 Personal、Plugin、System 或 Agent Copy，仍合并为一条逻辑记录，并显示所有来源标签。

详情页应增加只读来源说明：

```text
Provided by Codex Plugin
```

如果能稳定拿到插件展示名，则显示：

```text
Provided by Plugin: Superpowers
```

Plugin 详情页允许：

- 查看 `SKILL.md`
- 查看文件列表
- Reveal in Finder
- Copy Path

Plugin 详情页不允许：

- 安装到 Agent
- 卸载
- 删除
- 编辑源文件
- 更新插件
- 宣称 SkillDock 已完整安装插件

## Data And Merge Rules

合并规则沿用 V0.6.0：

- 合并键：规范化名称 + 内容 Hash。
- 同名同 Hash：合并为一条逻辑 Skill，保留全部物理来源。
- 同名不同 Hash：保持多条记录。
- Available 计数包含 Personal、Plugin、System 的去重逻辑记录。
- Installed 计数只看 Agent Target 副本，不因 Plugin 出现而增加。

如果未来需要展示插件名和版本，应新增轻量来源元数据，而不是把插件信息塞进 Skill 名称或路径文案。

## Error And Empty States

Plugin 来源未启用或无稳定元数据时：

- `Plugin` 筛选显示空状态。
- 文案说明 SkillDock 当前没有找到可稳定识别的 Plugin Skills。

单个插件解析失败时：

- 不影响其他来源。
- 在扫描问题中记录插件路径和失败原因。
- 不把失败插件显示为 0 个而无解释。

多个版本无法判定当前版本时：

- 不展示该插件的 Skills。
- 记录为待确认问题，避免把旧缓存误认为可用。

## Testing And Acceptance

后续实施计划至少应覆盖：

- 可从插件清单读取 `skills` 相对路径。
- 只扫描清单声明的 skills 目录。
- 插件无 `skills` 字段时跳过。
- 插件清单解析失败时保留其他来源。
- Plugin Skill 进入 Available，但不进入 Installed。
- Plugin 与 Personal/System 同名同 Hash 时合并并保留来源标签。
- Plugin 同名不同 Hash 时保持独立记录。
- Plugin 详情只读，所有写入入口被隐藏或阻断。
- 不存在全量扫描 `.codex/plugins/cache` 的实现路径。

产品验收至少覆盖：

- Available 的 Plugin 来源不会让用户误以为 SkillDock 管理插件安装。
- 空状态和详情文案能解释 Plugin 的只读边界。
- Personal、Plugin、System、Agent Copy 的标签不会混淆。

## Open Questions

- Codex 是否提供稳定的插件安装清单或启用状态接口。
- `.codex-remote-plugin-install.json` 与 `.codex-plugin/plugin.json` 是否可作为长期兼容契约。
- 多版本插件目录并存时，哪一个版本代表当前可用能力。
- 已安装但被禁用的插件是否仍会保留在 cache 中。

## Delivery Boundary

V0.6.1 的完成标准是设计和可行性结论清楚、可交接、可用于写实施计划。

只有当后续确认稳定来源和版本判定规则后，才进入真实 Plugin Skill 扫描实现。
